# Sponsor technology: how Probity uses Zetaris, Meterless and NVIDIA

Product: Probity, team Zen, Open Agent Hackathon 2026, track T01 Solving Fragmented Intelligence, also entered for Best use of NVIDIA Nemotron.
Written 2026-10-27. This is the text of the HackOS "sponsor technology" field; the narration and the deck use the same wording.
Numbers marked *measured* come from our logs and scripts (file named beside them). Nothing here is a claim beyond those files and `VERIFIED_FACTS.md`.

## 1. Zetaris

Every registry and ledger fact in a decision comes from Zetaris. (The one exception is the USAspending name search, an app adapter used only to find candidate UEIs; it is never cited as a fact.) Three sources that disagree sit behind one access point: USAspending recipient records and SEC EDGAR filings as Zetaris REST tables (USAspending read directly with `HEADER Accept application/json`; both activated through views over the REST tables), and our vendor master and AP ledger (generated data) as a Postgres datasource read in place over JDBC. A Unified Semantic Layer, `vendor360` (12 tables, one `COMPILE USL`), joins them on the keys that matter for payments: vendor id, UEI and CIK. The agents never write SQL. The Registry Scout picks from an allow-list of templates; the Evidence Runner sends each one to the Zetaris REST API with a query-only key and records its `query_id`, SQL hash and row hash. Every registry and ledger fact in a decision therefore traces to rows Zetaris returned, and every fact cell has a "Re-run in Zetaris" button.

Zetaris is also how the agent discovers. When the Examiner finds the claimed address in no known record, a coverage rule walks the vendor's corporate family (41 Booz Allen children, re-counted against the live USAspending endpoint on 2026-10-27), narrows it by the claimed state and registers that sibling's USAspending record as a Zetaris REST session table during the check (in the hero run, `session.pp_usa_r_khk6e1jw9c15`), then queries it. The family walk is code-issued; the Scout, on Nemotron 3.5 Lightning, adds checks on top of it.

Data-quality rules do business work. `RUN DQ unverified_recent_bank_change` and `RUN DQ account_single_vendor` over the payment run are the unsolicited sweep shown on every decision; in the Booz Allen request they find a different vendor already holding the requested account, which no single source shows. Four more registered rules check data quality outside the sweep: `request_routing_valid` (ABA checksum of each requested routing number) and three on real registry rows (`registry_has_address`, `sec_ein_present`, `sec_state_of_inc_present`). Since the depth work the sweep also runs DQ7 (one bank account on file for two vendors; it names the vendor ids), DQ8 `bank_change_before_large_payment` (registered with `REGISTER DQ`) and DQ9 (payee name differs from the vendor master), and a federated vendor profile (T23) reads ERP, USAspending and SEC EDGAR tables registered in Zetaris in one query; the ERP leg is read over JDBC at query time (`zetaris/results/d3-wire-live.json`). T23 is informational: it never changes a decision. Registration runs under an admin key only inside an allow-listed adapter. On this edition one Zetaris key fills both roles, so the query/admin split is enforced in code only.

## 2. Meterless Engines

**World Model** (the required engine) is the shared state. Vendors, legal entities, registrants, accounts, phones and domains are entities keyed by their real identifiers, so a name can never merge two companies. Edges are bitemporal: when the vendor master's phone changed by email three days before the letter, the old edge closed, and the call-back selector asks the World Model which number was on file 30 days before the request. Link verdicts from the Examiner are facts with provenance. A confirmed impersonation is written as a fact, and a later request in a separate process that reuses the same account, phone or domain is held, with a chip naming the earlier session.

Code: `vendor/meterless/world-model/` (the Meterless reference implementation, vendored unchanged and re-exported by `app/engines/world-model/`) and our adapter `app/engines/wm-adapter.ts`. Test: the Meterless conformance suite and our feature tests, result pasted from `npm run test:engines`: World Model conformance `8/8 checks passed`, H-MEM conformance `13/13 checks passed` (H-MEM is vendored but disabled in the product), and `vitest run tests/engines`: `Test Files 9 passed (9)`, `Tests 60 passed (60)` (2026-10-27 18:41Z).

## 3. Meterless Nightshift

Nightshift is the primary AI provider. The app calls its OpenAI-compatible runtime with the Bearer runtime token, a per-call `meterless-app: probity-<run_id>-<n>`, `meterless-scope: app` and `meterless-trace: 1`. Each lane is pinned to an exact Nemotron model id, `nvidia/nemotron-3.5-lightning-30b-a3b` and `nvidia/nemotron-3-ultra-550b-a55b`, both listed by Nightshift's `/v1/models`, so every receipt shows a single-candidate route to NVIDIA; no `meterless/*` routing id is ever used. Every call logs the requested model and the model Nightshift returned, with tokens and latency, into the run trace and the on-screen model ledger. A call answered by a non-Nemotron model is flagged amber and the run is marked `partial_success`. Nightshift can run an internal cross-check verifier on high-risk calls; it did not run on any receipt we recorded (`verifier_ran: false`). With `meterless-scope: user`, Nightshift's answer memory (H-MEM) injected earlier answers into new prompts; with scope `app` and a per-call app id it injects none, and every live run reports H-MEM injected 0.

## 4. NVIDIA Nemotron

Nemotron does four specific jobs, each visible in the UI and logged per call:

1. **Nemotron 3 Ultra** reads the bank-change letter twice, independently: reading A from the PDF text layer, reading B from the OCR of the rendered page, with different instructions. Code reconciles them field by field; a disagreement on a payment field (C7) stops the change until a person compares the letter. Each claim carries a verbatim quote and a page region the UI highlights; the email headers are parsed by code, and code checks every value against its quote.
2. **Nemotron 3.5 Lightning** reviews a code-issued coverage floor and adds evidence checks as native tool calls against Zetaris templates; in 17 recorded runs, 29 of 317 planned steps were chosen by Nemotron through a tool call, 102 were required by a coverage rule in code and 186 were fixed code steps (`docs/eval.md`).
3. **Nemotron 3 Ultra** reviews identity links that rules cannot settle (a former name, an alias shared by two companies) over rows the Examiner has just re-queried, and can only tighten, never loosen, a decision.
4. **Nemotron 3.5 Lightning** writes the rationale; code checks every number, phone and id in it against the decision before it is shown.
5. **Nemotron 3 Ultra** confirms the reviewer-instruction spans that code finds in a letter or email (hidden 1 pt text, text addressed to an automated reviewer). It can add a span but cannot remove one code found; any confirmed span is reason code R8, a HOLD that a call-back does not clear.

Measured per decision, on the live runs of 2026-10-27 at 18:37Z to 18:49Z: the Booz Allen check made 13 Nemotron calls (5 Ultra, 8 Lightning) and decided in 222 s; the hidden-instruction letter 9 calls (167 s); the L3Harris approval 6 calls (149 s). Every receipt shows egress `nvidia` and H-MEM injected 0. Measured quality: on the first evaluation (`docs/evidence/nemotron-eval.md`) Ultra answered 12 of 12 letters with 72 of 72 decisive fields exact and Lightning 3 of 12. The per-step table (`docs/evidence/model-per-step.md`, Lightning against Ultra on the same real inputs, small samples) shows Ultra right on 184 of 184 decisive fields on the 30 of 36 reads it answered, against 41 of 76 for Lightning on 14 of 34; on Examiner critique Ultra got 8 of 8 recorded and 6 of 6 control verdicts right, while Lightning with thinking on approved 3 links that should be blocked. Those Examiner labels were written by our coding assistant from the scenario design, not by an expert. On 34 adversarial and clean letters (`docs/evidence/adversarial-eval.md`) injected text was counted on 10 of 11 spans, all 5 hidden spans included, every injected letter was flagged, and 2 of 25 clean letters were flagged falsely. A name-to-CIK lookup (`sec_ticker_v`) is built, but no recorded decision uses it yet.

## 5. What was unique (Cursor was not used)

Cursor was not used. We built with Grok (xAI), which built the Zetaris data layer and the end-to-end tests, and Claude Code, which built the agents and interface (see the README, section 16).

What was unique:

- The call-back number is chosen by provenance, not by convenience: only an SEC-registered number, or one on file for 30 days before the request, enforced with a World Model point-in-time query. The letter's numbers and a recently changed master number are listed as "do not use", with reasons.
- A Zetaris DQ rule is the unsolicited action: the sweep of the whole payment run is `RUN DQ`, joining an account claimed in the letter to every other vendor's accounts.
- Discovery is narrowed by the claim: a coverage rule walks the vendor's family (41 Booz Allen entities), keeps only the one in the claimed state, and registers that sibling's USAspending record as a Zetaris session table during the check. The real address turns out to belong to a sibling that has never billed us.
- When the sources cannot say which vendor a request belongs to, it refuses to guess and writes one call-back script per candidate.
- As a baseline, before a newly discovered link counts, the Examiner re-runs its decisive Zetaris queries itself (at most four per run) and compares row hashes; a drift blocks the fact.
